# Migration Plan: vitest 3.2.7 → 4.1.11

**Date:** 2026-08-26
**Agent:** kirei-migrate
**Target:** `vitest` `^3` (resolved 3.2.7) → `^4` (target 4.1.11)
**Migration guide:** https://vitest.dev/guide/migration.html
**Release notes:** https://vitest.dev/blog/vitest-4

## Summary

`vitest` is a devDependency in 9 of 13 workspace packages (the 8 `eslint-plugin-*`
packages plus `eslint-test-utils`), used exclusively to drive
`@typescript-eslint/rule-tester` through a single shared shim
(`packages/eslint-test-utils/src/ruleTester.ts`). Direct vitest API usage outside
that shim is effectively one file (`packages/eslint-plugin-react/tests/rules/props-must-be-visual.test.ts`,
using only `describe`/`it`/`expect`, none of which changed shape in v4). Of the ~30
breaking changes catalogued in the official v3→v4 migration guide, only two are
even reachable by this repo's actual usage (config shape, still an even-then-inert
`restoreMocks` behavior tweak), and both were verified inert. The riskiest item —
whether the `RuleTester.afterAll/describe/describeSkip/it/itOnly/itSkip = <vitest exports>`
static assignment still type-checks and runs against `@typescript-eslint/rule-tester@8.68.0`
— was verified **empirically** in an isolated `/tmp` scratch install (`bun add
vitest@4.1.11 @typescript-eslint/rule-tester@8.68.0`, repo's exact `tsconfig.base.json`
compiler options, plus a live `RuleTester.run(...)` under real `vitest run`): it
**compiles clean under `--strict` and passes at runtime**. This is a low-risk,
single-PR, mostly-mechanical version-string bump. No published package requires a
version bump and no changeset is warranted (see "Published-Package Impact" below).

## Corrections to the initial scouted map

Two claims in the initial scout turned out to need correction on inspection:

1. **`eslint-test-utils` declares `vitest` as a `peerDependency`, not devDependency-only.**
   `packages/eslint-test-utils/package.json` has `"peerDependencies": { "vitest": "^3" }`
   *and* `"devDependencies": { "vitest": "^3" }` — both, not devDependency-only. This
   doesn't change the consumer-visibility conclusion, because `eslint-test-utils` is
   itself `"private": true` and is never published — a declared peer on an unpublished
   package has no external consumer. But the "devDependency ONLY across all 9 packages"
   framing was imprecise for this one package; flag both fields for the manual edit.
2. **`packages/lint-meta-rules/tests/rules/test-runner-segregation.test.ts` contains the
   substring `from 'vitest'`.** It is not an actual import — it's a string-literal test
   fixture (`"import { test } from 'vitest';"`) fed into a lint-meta rule that itself
   *checks* for cross-runner imports. Confirmed `lint-meta-rules` has zero real vitest
   dependency and is unaffected, as originally stated.

## Pre-flight Requirements

- **Runtime:** vitest 4.1.11 declares `engines.node: "^20.0.0 || ^22.0.0 || >=24.0.0"`.
  This repo's tests never run under a real Node process — `bun run test` executes the
  `vitest` bin (a `.mjs` file) directly under Bun's own runtime, and `process.version`
  under Bun 1.3.14 reports `v24.3.0` (verified: `bun -e "console.log(process.version)"`),
  which satisfies vitest 4's range. `.github/workflows/release.yml` additionally installs
  a real Node 22 via `actions/setup-node@v5`, but that Node is only in `PATH` for the
  `changesets/action` publish step, not for `bun run test`. **No runtime bump is
  strictly required to pass CI.** See "Housekeeping" below for the advisory-only
  `engines.node` gap.
- **Peer deps:** vitest 4.1.11 peer-requires `vite: "^6.0.0 || ^7.0.0 || ^8.0.0"`. The
  lockfile already resolves `vite@7.3.6` — already compatible, no bump needed.
- **@typescript-eslint/rule-tester:** already at 8.68.0 in the pending (uncommitted)
  `bun.lock` diff in this working tree — the version this plan's empirical type-check
  was run against. Do not disturb that pending diff; land this migration on top of it.
- **No other plugins/extensions to bump in lockstep.** No `@vitest/coverage-*`,
  `@vitest/ui`, `@vitest/browser*`, `msw`, `jsdom`, or `happy-dom` are used anywhere in
  this repo (grepped `package.json` + `vitest.config.ts` across all packages — zero hits).

### BC-1 — `RuleTester` statics wired to vitest's `describe`/`it`/`afterAll` and their `.skip`/`.only`

**Type:** Behavioral (but empirically verified inert — no shape change)
**Call site:** `packages/eslint-test-utils/src/ruleTester.ts:12-18`
```ts
import { afterAll, describe, it } from 'vitest';

RuleTester.afterAll = afterAll;
RuleTester.describe = describe;
RuleTester.describeSkip = describe.skip;
RuleTester.it = it;
RuleTester.itOnly = it.only;
RuleTester.itSkip = it.skip;
```
**Verification performed:** In an isolated `/tmp` scratch project (not the repo), ran
`bun add -D vitest@4.1.11 @typescript-eslint/rule-tester@8.68.0 @typescript-eslint/parser@8.68.0`,
copied this exact file plus the repo's exact `tsconfig.base.json` compiler options
(`strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`, `moduleResolution: Bundler`,
`skipLibCheck: true`), and ran `tsc --noEmit` — **zero errors**. Then wrote a minimal
rule + `ruleTester.run(...)` test file, copied the repo's exact `vitest.config.ts`
content verbatim, and ran `vitest run` — **2/2 tests passed**. `describe`, `it`,
`afterAll` (and `describe.skip`, `it.only`, `it.skip`) are still exported unchanged
from vitest's root entry (`@vitest/runner`'s `describe: SuiteAPI`, `it: TestAPI`,
`afterAll` re-exported through `vitest`'s `index.d.ts`), and their signatures remain
structurally assignable to `@typescript-eslint/rule-tester@8.68.0`'s
`RuleTesterTestFrameworkFunction` / `RuleTesterTestFrameworkItFunction` / `AfterAll`
static types.
**Fix:** None required — file is forward-compatible as-is. No code change to
`ruleTester.ts`.
**Residual risk:** None found for the *current* test corpus. Note for future authors:
no test file today uses `{ only: true }` / `{ skip: true }` in a `RuleTester` test
case (grepped, zero hits), so the `itOnly`/`itSkip`/`describeSkip` code paths aren't
runtime-exercised by the existing 602 tests even though they type-check — if a future
PR adds an `only`/`skip` case, it will be the first real exercise of those paths under
v4.

### BC-2 — `restoreMocks: true` semantics: `vi.restoreAllMocks()` no longer restores automocks

**Type:** Behavioral, confirmed **not reachable** by this repo's test corpus
**Call sites:** all 8 `vitest.config.ts` (`test.restoreMocks: true`)
**Detail from migration guide:** "`vi.restoreAllMocks()` only restores manually created
spies; automocks no longer affected." The `restoreMocks: true` config flag is
equivalent to calling `vi.restoreAllMocks()` before every test.
**Fix:** None required. Grepped the entire repo (`vi.mock(`, `vi.fn(`, `vi.spyOn(`,
`vi.restoreAllMocks(`) — **zero matches** anywhere in `packages/eslint-plugin-*` or
`packages/eslint-test-utils`. Rule tests are pure AST/static-analysis assertions
through `RuleTester.run(...)`; no mocks or spies are created anywhere in the 602-test
corpus, so `restoreMocks: true` is a no-op today and remains a no-op after the
upgrade.

### BC-3 — Config shape (`test.include`, `test.environment`, `test.globals`, `test.restoreMocks`, `defineConfig` from `vitest/config`)

**Type:** Structural, confirmed **unaffected**
**Files:** all 8 byte-identical `vitest.config.ts` (verified via `find ... -exec md5`,
single hash `238f2b7a0b73060eae082322b98f0e49`)
**Fix:** None. `defineConfig` is still exported from `vitest/config` in 4.1.11 (this
exact import path was used, unmodified, in the empirical `vitest run` smoke test
above and executed cleanly). `test.include`, `test.environment: 'node'`,
`test.globals: false`, `test.restoreMocks: true` are all still valid top-level
`test.*` keys in v4 with unchanged meaning — none of the v4 config-shape breaking
changes (workspace→projects, poolOptions flattening, coverage.all/extensions removal,
browser `instances`) touch any key this repo's config sets. `test.exclude`'s new
(narrower) default of `node_modules`/`.git` only (v3 also excluded `dist`, `cypress`,
config files) is likewise moot: the config uses a positive `include: ['tests/**/*.test.ts']`
allowlist per package, and no package's `tests/` directory or build output overlaps
with `dist/`.

### BC-4 — `@vitest/*` companion package versions

**Type:** Mechanical (lockfile-only, no code touches these directly)
**Call sites:** `bun.lock` — currently pins `@vitest/expect`, `@vitest/mocker`,
`@vitest/pretty-format`, `@vitest/runner`, `@vitest/snapshot`, `@vitest/spy`,
`@vitest/utils` all at `3.2.7`, and `vite-node@3.2.4` (transitive, vitest 3 only —
removed entirely as a dependency in v4, replaced internally by Vite's Module Runner).
**Verified via npm registry:** vitest 4.1.11's `package.json` pins every one of these
companions to the **exact same version** `4.1.11` (`@vitest/spy`, `@vitest/utils`,
`@vitest/expect`, `@vitest/mocker`, `@vitest/runner`, `@vitest/snapshot`,
`@vitest/pretty-format` — all `"4.1.11"` exact, no range). None of these packages are
declared directly in any workspace `package.json` — they're pulled in transitively
through `vitest`'s own `dependencies`, so bumping the top-level `"vitest": "^4"` range
and running `bun install` is sufficient; bun's lockfile resolution will pick up the
exact-pinned companions automatically. No manual edits to these needed anywhere.
**Fix:** Handled automatically by the `vitest` version bump + `bun install` (not
`bun update` — see Tooling Hazard note below).

## Codemods Available

None published by the Vitest maintainers for the v3→v4 transition (checked
`vitest.dev` migration guide and blog — no `npx <codemod>` tooling referenced,
unlike some other major frameworks). All 4 reachable BCs above resolved to "no code

## Upgrade Order

1. Manually edit `"vitest": "^3"` → `"vitest": "^4"` in the 9 `package.json` files:
   the 8 `eslint-plugin-*` packages' `devDependencies`, plus `eslint-test-utils`'s
   **both** `devDependencies` and `peerDependencies` entries (10 edits across 9 files
   total — `eslint-test-utils/package.json` has 2 occurrences).
2. Run `bun install` (plain — **not** `bun update` in any form; see Tooling Hazard).
   This resolves `vitest@4.1.11` and its exact-pinned `@vitest/*` companions, and
   drops `vite-node` from the lockfile (removed as a vitest v4 dependency).
3. Diff the resulting `bun.lock` — confirm only `vitest`, `@vitest/*`, and their
   sub-dependency deltas changed (e.g. `tinyrainbow` 2.0.0→3.1.0, `tinyexec`
   0.3.2→1.0.2, `std-env` 3.9.0→4.x, `chai` 5.2.0→6.2.2, new `@standard-schema/spec`
   dep of `@vitest/expect`, `debug`→`obug` inside vitest's own tree) — and that
   nothing else already-pending in the tree (the `@typescript-eslint/*` 8.68.0 bump,
   the `@noctcore/harness` 0.2.0 bump, the other safe-bump lines) gets clobbered or
   reverted.
4. No manual code fixes needed for BC-1/BC-2/BC-3 (all verified inert). No codemod to
   run.
5. `bun run build && bun run typecheck && bun run test` across the workspace.
6. (Optional housekeeping, not required for green CI — see below.)

## Published-Package Impact — no version bump, no changeset

`vitest` is declared only in `devDependencies` (and, for `eslint-test-utils`, also
`peerDependencies` — but that package is `"private": true` and never published) across
all 9 affected packages. It never appears in any `dependencies` or in any *published*
package's `peerDependencies`. None of the 8 publishable `@noctcore/eslint-plugin-*`
packages change their runtime behavior, public API, or declared dependency surface as
a result of this bump — consumers installing these plugins never resolve `vitest` at
all. Per this repo's changesets convention (`.changeset/config.json`,
`updateInternalDependencies: "patch"` only fires for internal *workspace* dependency
bumps, not external devDependency bumps) and precedent (the currently-pending
`@typescript-eslint/*` 8.63.0→8.68.0 devDependency bump in this same working tree
carries **no changeset**), this migration should land **without a changeset** and
**without any package `"version"` bump**. Contrast with the separate pending
`@noctcore/harness` 0.1.0→0.2.0 bump, which *does* carry a changeset — because
`@noctcore/harness` is a real `dependency` of the published `lint-meta-rules` package,
unlike `vitest`.

## Housekeeping (optional, not a CI blocker)

Root `package.json` declares `"engines": { "node": ">=22" }`, which admits Node 23 —
outside vitest 4's `^20.0.0 || ^22.0.0 || >=24.0.0` declared range (the gap is exactly
Node 23.x). In practice this is inert today because `bun run test` never invokes a
real Node.js process for the test run (Bun executes the `vitest` `.mjs` bin directly
under its own runtime, reporting `process.version` as `v24.3.0` under Bun 1.3.14,
verified). Bun does not enforce `engines` by default (no `bunfig.toml` / `.npmrc`
`engine-strict` found), so this is advisory only. If tightened, the more accurate
range would be `"node": "^20.0.0 || ^22.0.0 || >=24.0.0"` (matching vitest 4 exactly)
or simply `">=24"` if the team wants a single floor. Not required for this migration
to land green; call out separately if wanted.

## Tooling Hazard (carried over from task briefing — reconfirmed applicable here)

Do **not** use `bun update` in any form for this migration. On Bun 1.3.14 it has been
observed rewriting *published* `peerDependencies` ranges (e.g. narrowing
`eslint: ">=9.0.0"` to `eslint: "^10.7.0"`) as a side effect of an unrelated bump. The
verified-safe mechanic is: manually edit the 9 `package.json` `"vitest": "^3"` →
`"^4"` strings (10 occurrences, see Upgrade Order step 1), then run plain
`bun install`. This is the same mechanic already used for the pending
`@noctcore/harness` 0.2.0 bump in this working tree — follow that precedent exactly.

## Rollback

Single, small, mechanical diff: 9 `package.json` one-line-each edits (10 lines in
`eslint-test-utils`) + the resulting `bun.lock` delta. If `bun run test` regresses
post-upgrade (unexpected, given the empirical pre-verification above), revert is
`git checkout -- <the 9 package.json files> bun.lock` (scoped to just this migration's
files — do **not** blanket-revert `bun.lock`, since it also carries the pending
unrelated safe-bump diff and the harness 0.2.0 bump that must be preserved) followed
by `bun install`. No data migrations, no runtime feature flags — this is devDependency
-only, so rollback has zero blast radius outside the test-running toolchain itself.

## Out of Scope

- The already-pending, uncommitted `bun.lock` safe-bump diff (postcss, nanoid,
  brace-expansion, js-yaml, `@typescript-eslint/*` 8.63.0→8.68.0,
  `@changesets/cli` 2.31.1) and the `@noctcore/harness` 0.2.0 bump + its changeset —
  not touched or re-litigated by this plan, only preserved.
- `vite` itself (already compatible at 7.3.6, no bump needed).
- Root `engines.node` tightening (flagged as optional housekeeping only).
- `packages/lint-meta-rules` (uses `bun test`, zero real vitest dependency, confirmed
  unaffected).
- Any vitest coverage, browser-mode, UI, or reporter configuration (none exists in
  this repo).

## Outcome — applied 2026-08-26

All **10** `"vitest": "^3"` → `"^4"` occurrences edited across 9 packages (`eslint-test-utils` carries it in both `devDependencies` and `peerDependencies`; it is `private: true`, so unpublished). Lockfile regenerated with plain `bun install` — never `bun update`.

Resolved: `vitest@4.1.11` plus `@vitest/{expect,mocker,pretty-format,runner,snapshot,spy,utils}@4.1.11`, all exact-pinned. `vite@7.3.6` untouched and within v4's `^6 || ^7 || ^8` peer range.

**Zero code changes were required.** The `RuleTester.afterAll/describe/describeSkip/it/itOnly/itSkip` shim at `packages/eslint-test-utils/src/ruleTester.ts` — the single point gating typecheck across all 8 plugin packages — held under v4 with no edit.

`vite-node` (removed in v4) is confirmed gone: zero references in `bun.lock`, and a clean `rm -rf node_modules && bun install --frozen-lockfile` leaves only `vitest@4.1.11` in the store. A transient `vitest@3.2.7` / `vite-node@3.2.4` sighting in `node_modules/.bun/` was stale cache from the pre-upgrade install, not a live resolution.

Gates green on a clean install: build, typecheck (0 errors), **602 vitest tests** (react 157, contracts 114, architecture 100, code-quality 78, async-safety 69, observability 32, security 27, monorepo 25) + **84 bun tests** — matching baseline exactly, 0 failures.

**No version bump, no changeset.** vitest is devDependency-only in every published package.
