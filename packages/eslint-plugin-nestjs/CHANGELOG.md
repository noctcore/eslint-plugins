# @noctcore/eslint-plugin-nestjs

## 0.3.0

### Minor Changes

- [#246](https://github.com/noctcore/eslint-plugins/pull/246) [`74f4b74`](https://github.com/noctcore/eslint-plugins/commit/74f4b744f46e07c2ac2cae114da3bb11b85b36b2) Thanks [@Shironex](https://github.com/Shironex)! - Add `job-options-must-set-attempts`, an opt-in rule that reports a BullMQ `<queue>.add(name, data, options)` or `<queue>.addBulk([...])` job whose options and queue defaults set no `attempts`, so a single transient failure would lose the job. The call's options are laid over the `defaultJobOptions` of a `new Queue(...)` imported from `bullmq` and stored in the same binding in the same file; defaults set anywhere else are not seen. With `requireBackoff` (default `true`), a number `attempts` other than `1` must also come with a `backoff`. Options or `addBulk` jobs that are not object literals, a spread that may hold the missing key, an `attempts` that is not a number literal and any `FlowProducer` call are skipped; in `addBulk`, only the elements of the list (or what a `map` / `flatMap` callback returns) count as jobs; `queuePattern` picks which receivers count as queues, as in the other queue rules. The rule is not in `recommended`, so it adds no errors to a project spreading `recommended`.
  
  The shared `this` resolver no longer throws on a `this` at the top level of a file, which crashed `worker-must-listen-failed` on code such as `this.worker.on('failed', handler)` outside a class. Such a file now lints instead of failing with a crash, so `worker-must-listen-failed` can report it as it would any other file, for example `missingListener` on a top-level `this.worker = new Worker(...)` with no `failed` listener.

- [#247](https://github.com/noctcore/eslint-plugins/pull/247) [`96fcf50`](https://github.com/noctcore/eslint-plugins/commit/96fcf50870127500bce914ef5f8d9ecf741161cb) Thanks [@Shironex](https://github.com/Shironex)! - Add `queue-options-must-set-retention`, an opt-in rule that reports a BullMQ `<queue>.add(name, data, options)` job whose options and queue defaults leave out `removeOnComplete` or `removeOnFail`, so finished jobs would pile up in Redis. One report per call names every missing key, and the `require` option (default both keys) narrows which keys are checked. A literal `false` counts as set, since keeping finished jobs on purpose is a valid choice; only a missing key, or a value of `undefined`, is reported. The call's options are laid over the `defaultJobOptions` of a `new Queue(...)` imported from `bullmq` and stored in the same binding in the same file; defaults set anywhere else (`BullModule.registerQueue`, another file) are not seen. Options or `defaultJobOptions` that are not object literals, a spread that may hold the key, `addBulk` calls and flow objects passed to `add` are skipped; `queuePattern` picks which receivers count as queues, as in the other queue rules. The rule is not in `recommended`, so a project spreading `recommended` sees no new errors.

- [#248](https://github.com/noctcore/eslint-plugins/pull/248) [`704501e`](https://github.com/noctcore/eslint-plugins/commit/704501e3a916ecd89ff54a2531ebdb1cfbfe1cd0) Thanks [@Shironex](https://github.com/Shironex)! - Add `worker-concurrency`, an opt-in rule that reports a literal BullMQ worker `concurrency` of 0 or below (`0`, `-0`, `-1`) or that is not a whole number (`2.5`), in the options of a `new Worker(name, processor, options)` imported from `bullmq` (renamed imports count, a `Worker` from elsewhere does not) and in the second argument of `@Processor(queue, options)`. With `requireExplicit` (default `false`), a worker whose options literal has no `concurrency` key, or that has no options, is reported too. Values that are not number literals (identifiers, member accesses, calls, strings), options passed by name, a spread that may hold the key, `new bullmq.Worker(...)` through a namespace import, the `worker.concurrency = n` setter and the first-argument object of `@Processor({ name, ... })` are skipped. The rule is not in `recommended`, so a project spreading `recommended` sees no new errors; turn it on with `'noctcore-nestjs/worker-concurrency': 'error'`.

- [#249](https://github.com/noctcore/eslint-plugins/pull/249) [`e2ba660`](https://github.com/noctcore/eslint-plugins/commit/e2ba66096869f342c97cac24952e7851ae9bdd79) Thanks [@Shironex](https://github.com/Shironex)! - Add `redis-client-from-factory`, an opt-in rule that reports a `new Redis(...)` or `new IORedis(...)`, and the inline `connection: { ... }` object of a BullMQ `new Queue(name, options)` or `new Worker(name, processor, options)`, whose options do not come from a configured factory call. A factory call is accepted directly or as a spread inside an object literal (`new Redis(getRedisOptions())`, `new Redis({ ...getRedisOptions(), db: 1 })`). A client with no argument, a literal or template literal, a call to an unlisted function, or an object literal with no factory spread is reported; an identifier or member expression is not followed and not reported. `Queue` and `Worker` are recognised by their `bullmq` import, renamed or not. The rule needs `factoryFunctions` (the names of your options factories) and does nothing until it is set; `clientClasses` replaces the default `Redis`, `IORedis`, and `allowIn` replaces the default of test files, so add the module that defines the factory to it. The rule is not in `recommended`, so a project spreading `recommended` sees no new errors.

## 0.2.0

### Minor Changes

- [#234](https://github.com/noctcore/eslint-plugins/pull/234) [`c7d704d`](https://github.com/noctcore/eslint-plugins/commit/c7d704d4fa39b24b500b5dff4b3af857ba288482) Thanks [@Shironex](https://github.com/Shironex)! - Add two BullMQ worker rules, both on in `recommended` at `error`. A project spreading `recommended` will see new errors.
  
  `worker-must-listen-failed` reports a `new Worker(...)` imported from `bullmq` (renamed imports included) that has no `.on('failed', ...)` listener in the same file, and a `new Worker(...)` written as a bare statement with nothing chained on it. A listener chained on the constructor or attached through the same binding (`worker.on(...)`, `this.worker.on(...)`, `addListener` and `prependListener` too) anywhere in the file counts, and so does a worker that is returned, passed to a function or stored in another binding. Bindings are resolved through scope, so two workers named `worker` in different functions are checked apart, while `this.worker` is shared with a base class or subclass declared in the same file, so a base service that wires the listeners covers its subclass's worker. A worker held in a field of a class whose base comes from another module is not reported, since that base may listen. A listener whose event name is not a static string (an enum member, a loop variable) counts for every event. NestJS `@Processor` classes extending `WorkerHost` are not affected. To fix a report, add `worker.on('failed', (job, err) => logger.error({ jobId: job?.id, err }))` or chain it on the constructor. The `requiredEvents` option (default `['failed']`) can ask for more events.
  
  `worker-must-implement-close` reports a class that creates a `bullmq` `Worker` in an instance field (a field initialiser, or `this.worker = new Worker(...)` in a method) when none of its close methods calls `this.worker.close()`, directly, through a local alias (`const self = this` included) or through a helper method it calls on `this` or `super`. A worker the close method passes to a function (`closeQuietly(this.worker)`) or puts in an array literal counts as closed there. A close method inherited from a base class in the same file counts; a class extending a base from another module or a `declare class`, or with an abstract close method, is not reported. The default close methods are `close`, `shutdown`, `dispose`, `onModuleDestroy`, `onApplicationShutdown` and `beforeApplicationShutdown`; `closeMethodNames` replaces the list. To fix a report, add `async onModuleDestroy() { await this.worker.close(); }`.
  
  To keep the old behaviour, turn either rule off after spreading the preset: `'noctcore-nestjs/worker-must-listen-failed': 'off'` or `'noctcore-nestjs/worker-must-implement-close': 'off'`.

## 0.1.0

### Minor Changes

- [#160](https://github.com/noctcore/eslint-plugins/pull/160) [`f9378ce`](https://github.com/noctcore/eslint-plugins/commit/f9378ce59135d6dabcf8844ec98b8da7b31431ea) Thanks [@Shironex](https://github.com/Shironex)! - New package `@noctcore/eslint-plugin-nestjs` for NestJS and BullMQ background work, starting at 0.1.0 with three rules:
  
  - `schedule-states-time-zone` (in `recommended` at `error`): a `@Cron` states `timeZone` (or `utcOffset`), and a BullMQ `upsertJobScheduler` or `repeat: { pattern }` states `tz`. The `zones` option restricts which zones may be stated.
  - `queue-add-requires-dedup-key` (opt-in): every `<queue>.add` / `.addBulk` job carries a `jobId` or `deduplication` in literal options.
  - `job-name-must-be-constant` (opt-in): queue and job names in `@Processor`, `@InjectQueue` and `<queue>.add` are shared constants, not inline strings.
