# `noctcore-architecture/no-restricted-imports-layered`

> Import bans declared once as named sets and assigned to file layers, merged per file instead of overridden, covering static imports, re-exports and dynamic `import()`.

## In short

You declare each import ban once, as a named set, and say which file layers it applies to. When
several layers match a file, all their bans apply together instead of the last one winning, and
dynamic `import()` is covered too.

and `{{message}}` the ban's own `message`, when it has one.

## Code that triggers it

Flat config does not merge `no-restricted-imports` across config blocks. For a given file, the last
matching block's options replace every earlier block's. A repo that bans an SDK everywhere and then
adds a layer ban for one directory has to repeat the SDK ban inside the layer block, and the copies
drift apart. The built-in rule also never sees a dynamic `import()`, so the same bans get written a
second time as `no-restricted-syntax` selectors.

This rule takes the bans once, as named sets, and the layers as a list of `files` / `ignores` globs
that name the sets they apply. Every layer that matches a file contributes its sets, so bans merge
instead of overriding one another.

The second covers the same folder and ignores the codex provider folder; it applies the ban set codex. For run.ts both sets apply, so importing either SDK is reported. With flat config blocks of no-restricted-imports, the second block would replace the first and only the codex ban would remain.](../diagrams/layered-bans.svg "Every layer that matches a file **adds** its ban sets. Flat config blocks would replace each other; this rule merges them.")

An import of a module that a ban set active for the file names is reported, on every
source-carrying construct:

- static `import … from '…'`, including a side-effect `import '…'`
- `export … from '…'` and `export * from '…'`
- dynamic `import('…')` with a string or a plain template literal

A module glob matches the specifier or any parent path of it, the way a `no-restricted-imports`
group does: `@/features` bans `@/features/billing`, and an SDK name bans its subpath exports.

### A module banned for the layer

```ts bad message=banned filename=src/lib/prefetch.ts reports=3 options={"bans":{"noFeatures":[{"modules":["@/features","**/features"],"message":"Move the shared piece down a layer."}],"noRoutes":[{"modules":["@/routes","**/routes"]}]},"layers":[{"files":["src/lib/**"],"bans":["noFeatures","noRoutes"]}]}
import { InvoiceList } from '@/features/billing';
import { useInvoice } from '../features/billing/hooks';
const screen = await import('@/routes/invoices');
```

```text report
`@/features/billing` is banned here (ban set `noFeatures`). Move the shared piece down a layer.

`../features/billing/hooks` is banned here (ban set `noFeatures`). Move the shared piece down a layer.

`@/routes/invoices` is banned here (ban set `noRoutes`).
```

**The fix:** move what `lib` needs down into `lib` itself and import it from there, so the lower
layer never depends on the ones above it.

```ts good filename=src/lib/prefetch.ts options={"bans":{"noFeatures":[{"modules":["@/features","**/features"],"message":"Move the shared piece down a layer."}],"noRoutes":[{"modules":["@/routes","**/routes"]}]},"layers":[{"files":["src/lib/**"],"bans":["noFeatures","noRoutes"]}]}
import { invoiceQuery } from './invoices';
const invoices = await import('./invoices/list');
```

Relative and aliased spellings are different strings, so list both: `@/features` for the alias and a
glob starting with `**` (`**/features`) for the relative form.

### Two layers that match the same file

Both apply. Here the engine core may use neither SDK, while each provider folder is exempt from its
own SDK's ban only:

```ts bad message=banned filename=packages/engine/src/session/run.ts reports=2 options={"bans":{"claude":[{"modules":["@anthropic-ai/claude-agent-sdk"]}],"codex":[{"modules":["@openai/codex-sdk"]}]},"layers":[{"files":["packages/engine/src/**"],"ignores":["packages/engine/src/providers/claude/**"],"bans":["claude"]},{"files":["packages/engine/src/**"],"ignores":["packages/engine/src/providers/codex/**"],"bans":["codex"]}]}
import { query } from '@anthropic-ai/claude-agent-sdk';
import { Codex } from '@openai/codex-sdk';
```

**The fix:** the core talks to the providers, and only each provider folder imports its SDK.

```ts good filename=packages/engine/src/session/run.ts options={"bans":{"claude":[{"modules":["@anthropic-ai/claude-agent-sdk"]}],"codex":[{"modules":["@openai/codex-sdk"]}]},"layers":[{"files":["packages/engine/src/**"],"ignores":["packages/engine/src/providers/claude/**"],"bans":["claude"]},{"files":["packages/engine/src/**"],"ignores":["packages/engine/src/providers/codex/**"],"bans":["codex"]}]}
import { runProvider } from '../providers';
```

### A banned name from an allowed module

With `importNames`, only those names are banned, each reported where it is imported. A namespace
import (`import * as`) and `export *` always count:

```ts bad message=bannedName filename=src/lib/query.ts reports=1 options={"bans":{"legacy":[{"modules":["@tanstack/react-query"],"importNames":["useQueries"]}]},"layers":[{"files":["src/**"],"bans":["legacy"]}]}
import { useQueries, useQuery } from '@tanstack/react-query';
```

```text report
`useQueries` from `@tanstack/react-query` is banned here (ban set `legacy`).
```

**The fix:** keep the names the ban allows and drop the banned one.

```ts good filename=src/lib/query.ts options={"bans":{"legacy":[{"modules":["@tanstack/react-query"],"importNames":["useQueries"]}]},"layers":[{"files":["src/**"],"bans":["legacy"]}]}
import { useQuery } from '@tanstack/react-query';
```

### A value import through a type-only ban

With `allowTypeImports`, a ban lets types through. An import that mixes a type specifier with a value
specifier is still reported:

```ts bad message=banned filename=src/features/billing/client.ts reports=2 options={"bans":{"api":[{"modules":["@api/*"],"allowTypeImports":true}]},"layers":[{"files":["src/**"],"bans":["api"]}]}
import { appRouter } from '@api/trpc';
import { type InvoiceInput, createInvoice } from '@api/billing';
```

**The fix:** import only types from the banned modules and reach the values another way.

```ts good filename=src/features/billing/client.ts options={"bans":{"api":[{"modules":["@api/*"],"allowTypeImports":true}]},"layers":[{"files":["src/**"],"bans":["api"]}]}
import type { AppRouter } from '@api/trpc';
import { type InvoiceInput } from '@api/billing';
```

## What it does not flag

- Files no layer matches, and files a layer's `ignores` excludes from it.
- With `allowTypeImports`, `import type`, `export type` and inline `type` specifiers.
- A module whose name only starts with a banned one (`@openai/codex-sdk-mock` against
  `@openai/codex-sdk`).
- A dynamic `import()` whose specifier is computed, since it cannot be resolved statically. A name
  ban never applies to a dynamic import, since the names it reaches are unknown.
- Anything, without options.

## Options

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `bans` | `Record<string, Ban[]>` | `{}` | Named ban sets, declared once and referenced by name from `layers`. |
| `layers` | `Layer[]` | `[]` | Which ban sets apply where. Every layer matching a file adds its sets. |

A `Ban`:

| Field | Type | Meaning |
| --- | --- | --- |
| `modules` | `string[]` | Globs matched against the specifier or any of its parent paths. Required. |
| `importNames` | `string[]` | Ban only these names (`default` for the default import). |
| `allowTypeImports` | `boolean` | Allow type-only imports and specifiers. |
| `message` | `string` | Appended to the report, usually what to import instead. |

A `Layer`:

| Field | Type | Meaning |
| --- | --- | --- |
| `files` | `string[]` | File globs the layer applies to, read relative to the working directory like flat-config `files`. A glob starting with `**/` also matches the absolute path. Required. |
| `ignores` | `string[]` | File globs excluded from the layer. |
| `bans` | `string[]` | Names of the ban sets that apply. A name `bans` does not declare is a configuration error. Required. |

```js
'noctcore-architecture/no-restricted-imports-layered': ['error', {
  bans: {
    claudeSdk: [{ modules: ['@anthropic-ai/claude-agent-sdk'], message: 'Only the claude provider talks to the SDK.' }],
    noFeatures: [{ modules: ['@/features', '**/features'] }],
    apiTypeOnly: [{ modules: ['@api/*'], allowTypeImports: true }],
  },
  layers: [
    { files: ['apps/**', 'packages/**'], ignores: ['packages/engine/src/providers/claude/**'], bans: ['claudeSdk'] },
    { files: ['apps/web/src/lib/**'], bans: ['noFeatures', 'apiTypeOnly'] },
  ],
}]
```

### In `recommended`

Left out of `recommended`. The rule does nothing without your own ban sets and layers, so there is no
default the preset could enable.

## When not to use it

If one `no-restricted-imports` block per file is enough, because no file sits under two layers with
different bans and you have no dynamic imports to cover, the built-in rule is simpler.
