# `noctcore-architecture/no-cross-feature-imports`

> A file in one feature may not import runtime code from another feature.

<!-- begin generated rule header -->
☑️ In `strict` at `error`, not in `recommended` · 💭 Type information: not needed
<!-- end generated rule header -->

## In short

Every folder directly under your feature root (`components` by default) is a feature. A file inside
one feature may not import runtime code from another. Shared code lives outside the feature root, or
in a shared feature (`ui` by default) that every feature may import.

`featureRoot` option.

## Code that triggers it

Features are meant to be decoupled: a change inside feature `board` should never be able to ripple
into feature `projects`. When one feature reaches directly into another's internals, that boundary
erodes and the two become one tangled unit.

Its import of ProjectCard from the projects feature crosses into a sibling feature and is reported.](../diagrams/feature-boundaries.svg "A feature may import **itself, the shared feature and code outside the feature root**. The one arrow the rule stops is the one into a sibling feature.")

For a file that lives under `<featureRoot>/<feature>/…`, the rule reports any import whose target
resolves to a **different** feature under the same root. Both the alias form (`<alias>/<feature>/…`)
and relative paths that climb into another feature (`../../projects/…`) are detected.

### An import from another feature

```tsx bad message=crossFeatureImport filename=src/components/board/Board/Board.tsx options={"featureRoot":"components","alias":"@/components","sharedFeatures":["ui"]}
import { ProjectCard } from '@/components/projects/ProjectCard'; // cross-feature
```

```text report
Cross-feature import: `board` may not import runtime code from `components/projects`. Move shared code to a shared module or a shared feature (e.g. `components/ui`).
```

**The fix:** move the card both features need into the shared feature (or into a module outside the
feature root, such as `@/lib`) and import it from there. `board` now depends on shared code, never on
`projects`.

```tsx good filename=src/components/board/Board/Board.tsx options={"featureRoot":"components","alias":"@/components","sharedFeatures":["ui"]}
import { ProjectCard } from '@/components/ui/ProjectCard'; // moved to the shared feature
import { Button } from '@/components/ui/Button';           // shared feature
import { cn } from '@/lib/utils';                          // non-feature module
import { TaskCard } from '../TaskCard/TaskCard';           // same feature
```

### A relative path that climbs into another feature

```tsx bad message=crossFeatureImport filename=src/components/board/Board/Board.tsx
import { ProjectCard } from '../../projects/ProjectCard/ProjectCard';
```

**The fix:** the relative spelling is the same dependency, so the fix is the same: import the shared
copy.

```tsx good filename=src/components/board/Board/Board.tsx
import { ProjectCard } from '../../ui/ProjectCard/ProjectCard';
```

### A re-export or a dynamic import

The check runs on every source-carrying construct: static `import … from '…'`, dynamic `import('…')`,
and `export … from '…'` or `export * from '…'`, so a re-export cannot launder the dependency.

```tsx bad message=crossFeatureImport reports=2 filename=src/components/board/Board/Board.tsx
export * from '@/components/projects/ProjectCard';
const panel = await import('@/components/projects/ProjectsPanel');
```

**The fix:** re-export and load only what belongs to the feature or the shared feature.

```tsx good filename=src/components/board/Board/Board.tsx
export * from '@/components/ui/ProjectCard';
const panel = await import('@/components/board/BoardPanel');
```

## What it does not flag

- Imports of the current feature, of a shared feature, or of non-feature modules (`@/lib/utils`, bare
  packages like `zod`).
- Type-only imports and re-exports, by default (flip `allowTypeImports` to forbid them).
- Files outside any feature, such as `routes/projects.tsx`.
- A dynamic `import(name)` whose source is not a string literal, since it cannot be resolved statically.

```tsx good filename=src/components/board/Board/Board.tsx
import type { Project } from '@/components/projects/types'; // type-only: allowed by default
```

## Options

| Option | Type | Default | Meaning |
| --- | --- | --- | --- |
| `featureRoot` | `string` | `'components'` | The directory segment whose immediate children are features. |
| `alias` | `string` | `'@/components'` | The import-alias prefix that maps onto `featureRoot`. |
| `sharedFeatures` | `string[]` | `['ui']` | Features every other feature is allowed to import. |
| `allowTypeImports` | `boolean` | `true` | When `true`, `import type` / `export type` cross-feature imports are permitted. |

```js
'noctcore-architecture/no-cross-feature-imports': ['error', {
  featureRoot: 'components',
  alias: '@/components',
  sharedFeatures: ['ui'],
  allowTypeImports: true,
}]
```

## When not to use it

If your app is not organized as sibling features under a single root, or you allow features to
depend on each other freely, this rule does not apply.
