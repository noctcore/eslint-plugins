# @noctcore/eslint-plugin-architecture

Folder-per-component and feature-boundary rules: catches the imports and file layouts that quietly
erode a feature-organised codebase. Framework-agnostic.

**Docs:** [noctcore.github.io/eslint-plugins/packages/architecture](https://noctcore.github.io/eslint-plugins/packages/architecture/)

Not a good fit for a codebase organised by technical layer (`hooks/`, `components/`, `utils/` at the
top) rather than by feature.

## Requirements

- ESLint 9 or 10, flat config (`eslint.config.js`) only.
- `configs.recommended` registers the plugin and sets rule severities, nothing else. It sets no
  `files` and no parser, so it applies to whatever files the rest of your config lints. To lint
  TypeScript, add a `files` pattern and `@typescript-eslint/parser`, as in the quick start.

## Install

```sh
bun add -D @noctcore/eslint-plugin-architecture @typescript-eslint/parser   # or npm i -D / pnpm add -D
```

## Quick start

```js
// eslint.config.js
import tsParser from '@typescript-eslint/parser';
import architecture from '@noctcore/eslint-plugin-architecture';

export default [
  {
    // `recommended` is empty: every rule here is a layout convention, see "Strict preset".
    ...architecture.configs.strict,
    files: ['**/*.{ts,tsx}'],
    languageOptions: { parser: tsParser },
  },
  // Optional: tune a preset rule's options.
  {
    files: ['**/*.{ts,tsx}'],
    rules: {
      'noctcore-architecture/component-folder-structure': ['error', { componentRoot: 'components' }],
      'noctcore-architecture/no-cross-feature-imports': ['error', { alias: '@/components' }],
    },
  },
];
```

Every rule anchors on a configurable directory segment (default `components`) rather than an absolute
path, so it behaves the same whether ESLint runs from the repo root or per-package, on POSIX or
Windows. Several rules inspect files on disk (sibling sets, barrel siblings, colocated tests), so run
ESLint against real file paths, not virtual sources.

## Strict preset

`configs.strict` is `recommended` plus the house rules: `barrel-purity`, `component-folder-structure`, `filename-matches-export`, `index-must-reexport-default`, `max-import-depth`, `no-cross-feature-imports`. A house rule holds in a codebase
that follows the same convention and reports widely in one that does not, so it is one spread away
instead of on by default.

Every rule in this plugin encodes a layout choice (file names, folder shape, feature boundaries, import
depth), so all of them live in `strict` and `recommended` turns nothing on. Spread `strict` if your
codebase follows the folder-per-component layout these rules describe, as the quick start does.

```js
// eslint.config.js
export default [
  {
    ...architecture.configs.strict,
    files: ['**/*.{ts,tsx}'],
    languageOptions: { parser: tsParser },
  },
];
```

**Upgrading to 1.0:** `recommended` no longer turns on `barrel-purity`, `component-folder-structure`, `filename-matches-export`, `index-must-reexport-default`, `max-import-depth`, `no-cross-feature-imports`. To keep the 0.x behaviour, spread
`configs.strict` where you spread `configs.recommended`, or enable the rules you want one by one.

## Opt-in rules

Two rules ship `off` because they are opinions many good codebases do not share, and two do nothing
until you configure them. Turn them on explicitly:

```js
// eslint.config.js
export default [
  // ...the quick start's entries, then:
  {
    files: ['**/*.{ts,tsx}'],
    languageOptions: { parser: tsParser },
    rules: {
      // Does nothing until `include` names the files that need a colocated test.
      'noctcore-architecture/colocated-test-required': ['error', { include: ['src/**/*.{ts,tsx}'] }],
      'noctcore-architecture/single-semantic-module': 'error',
      // Does nothing until `bans` and `layers` say which imports are banned where.
      'noctcore-architecture/no-restricted-imports-layered': ['error', {
        bans: { noFeatures: [{ modules: ['@/features', '**/features'] }] },
        layers: [{ files: ['src/lib/**'], bans: ['noFeatures'] }],
      }],
    },
  },
];
```

## Severity policy

Every rule is `error` or `off`, never `warn`: a warning is a rule nobody obeys. See the
[severity policy](https://noctcore.github.io/eslint-plugins/getting-started/#severity-policy).
