# @noctcore/eslint-plugin-three

three.js and React Three Fiber rules for the performance and leak defects that pass review and
every test: an uncapped pixel ratio, GPU resources that are never disposed or are rebuilt on every
render, allocations and React state updates in the frame loop, camera changes without
`updateProjectionMatrix()`, and instance writes that never reach the GPU.

**Docs:** [noctcore.github.io/eslint-plugins/packages/three](https://noctcore.github.io/eslint-plugins/packages/three/)

Not a good fit for code that does not use three.js. Every rule except
`capability-probe-performance-caveat` (a plain WebGL check) runs only in files that import `three`,
a `three/*` subpath, `three-stdlib` or an `@react-three/*` package; a project that re-exports
three.js through its own module names it in `extraModules`, and its named and namespace imports
then count as three.js classes and React Three Fiber hooks too. Only static `import` declarations
are read: a file that loads three.js only through `import()` or `require()` is skipped (a missed
report, never a false one). Matching is by syntax, without type information.

## Requirements

- ESLint 9 or 10, flat config (`eslint.config.js`) only.
- `configs.recommended` registers the plugin and sets rule severities, nothing else. It sets no
  `files` and no parser, so it applies to whatever files the rest of your config lints. To lint
  TypeScript and TSX, add a `files` pattern and `@typescript-eslint/parser`, as in the quick start.

## Install

```sh
bun add -D @noctcore/eslint-plugin-three @typescript-eslint/parser   # or npm i -D / pnpm add -D
```

## Quick start

```js
// eslint.config.js
import tsParser from '@typescript-eslint/parser';
import three from '@noctcore/eslint-plugin-three';

export default [
  {
    ...three.configs.recommended,
    files: ['src/**/*.{ts,tsx}'],
    languageOptions: { parser: tsParser, parserOptions: { ecmaFeatures: { jsx: true } } },
  },
];
```

## Opt-in rules

Two rules are left out of `recommended` because the right answer depends on the project: whether a
slow software renderer is better than a fallback page, and how large a shadow map your target
devices can afford.

```js
// eslint.config.js
export default [
  // ...the quick start's entry, then:
  {
    files: ['src/**/*.{ts,tsx}'],
    languageOptions: { parser: tsParser, parserOptions: { ecmaFeatures: { jsx: true } } },
    rules: {
      'noctcore-three/capability-probe-performance-caveat': 'error',
      'noctcore-three/shadow-map-size-cap': ['error', { maxMapSize: 2048 }],
    },
  },
];
```

## Severity policy

Every rule is `error` or `off`, never `warn`: a warning is a rule nobody obeys. See the
[severity policy](https://noctcore.github.io/eslint-plugins/getting-started/#severity-policy).
