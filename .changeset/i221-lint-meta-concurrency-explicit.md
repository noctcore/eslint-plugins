Add the `github-actions-concurrency-explicit` rule and its factory `createGithubActionsConcurrencyExplicitRule`. It reports a workflow-level or job-level `concurrency` mapping, written as a block or as a flow mapping, that has no `cancel-in-progress`, because whether a newer run cancels the running one is then left to GitHub's default instead of a stated choice. A `cancel-in-progress` with any value (`true`, `false`, or a `${{ }}` expression), a `concurrency` key nested deeper than a job's own keys, and a flow mapping that wraps over several lines are left alone. The string form `concurrency: ${{ github.workflow }}-${{ github.ref }}` passes by default and is reported at both levels when `requireMappingForm: true`. It takes `workflowGlobs` (default `.github/workflows/*.y(a)ml`), `requireMappingForm` (default `false`) and `ciCritical` (default `true`). lint-meta has no `recommended` preset, and a caller that picks factories one by one sees nothing new. The factory is part of `RULE_FACTORIES`, so `createAllRules()` now includes it: a caller of `createAllRules()` sees new violations on any `concurrency` mapping without `cancel-in-progress`. `github-actions-security-no-cancel` now reads `concurrency` through a shared reader, with no change in what it reports.
