---
'@noctcore/eslint-plugin-security': patch
---

`no-shell-interpolation` no longer reports a command whose every runtime part the function already proved harmless before the call, in the same function: a value checked by an exiting `if` (or an `if` around the call) against an allowlist of literals (`includes` on an array literal, `has` on a `new Set([...])`, `===` / `!==` against literals, `==` / `!=` against a string literal) or against a regex anchored at both ends, without the `m` flag, that admits no shell metacharacter and no whitespace, does not accept the empty string, and cannot start with `-` or `#` (a leading `-` or `#` is allowed only when the value is glued to text before it in the same word, such as `--author=${x}`, and that text does not end in `-` or `+`); the output of `schema.validate(x)` (with `if (error)` exiting) or `schema.parse(x)` when the schema chain only narrows and its `pattern` / `regex` is such a regex or it is a literal `valid` / `enum` / `literal`; or an in-file `const` literal. A value in a word that runs as a program is proven only by a literal allowlist, a literal schema set or a constant, never by a regex or schema pattern. That is the first word of a command (first in the string, after `;`, `&`, `|`, `(`, a backtick, a line break, `NAME=value`, a redirect such as `2>/dev/null` or a reserved word, including a value glued to a path such as `/usr/bin/${tool}`), and every word after a wrapper up to the next separator, options included: `sudo`, `doas`, `env`, `nice`, `timeout`, `xargs`, `time`, `eval`, `source`, `.`, `sh -c` and the other shells, `ssh`, `npx`, `pnpm dlx`, `find -exec` and the rest of the list in the rule docs, matched by basename and with quotes stripped. An in-file `const` string (`const SEP = ';'`) is read as its text. A value glued right after a `/` is a path segment and its regex must refuse `.` and `..`.

The proof is strict: a list in a `const` counts only if it is never exported or changed; a write to the checked binding after the check, from a nested function, or an in-place change (`push`, `x[0] = y`, `Object.assign`, `Reflect.set`, or the same through an alias) cancels it, and so does handing a checked array or object the function built to another function; a binding declared outside the checking function counts only if it is never written after its `let` or `const` declaration; a list or `Set` changed through another `const` name for it does not count; a count written `{00}` is read as optional like `{0}`; a parameter of a sloppy-mode function that uses `arguments` is never trusted; a direct `eval(s)` after the check (or in a nested function, or behind `eval!` / `as` / `satisfies` / `<T>`) counts as a write; a global the config declares writable is never trusted; a schema `const` counts only if every use runs it (`parse`, `safeParse`, `validate`), builds on it, or passes it to a schema builder whose result follows the same rules, so `S.parse = ...`, `S._def.checks.pop()`, `const d = S._def`, `patch(S)` or `B.shape.m.parse = ...` on a schema holding it cancels it, and the zod / joi root may only be called; a check outside a callback or above a hoisted function does not count inside it; and a schema chain with `default`, `catch`, `failover`, `pipe` or a `pattern` options argument, or one that does not start at the zod or joi import, is not read; a parsed object or `safeParse` result that is changed anywhere (`result.data = x`, `Object.assign(result, x)`, an alias), or a field a spread or later key can replace, does not count; an imported binding, an exported regex or one whose `test` is replaced is never trusted.

New option `trustEnvironment` (default `false`): leave values read from `process.env` with a fixed key alone. It is off by default because CI variables such as `GITHUB_HEAD_REF` hold outside input, so `` exec(`git checkout ${process.env.GITHUB_HEAD_REF}`) `` is still reported.

The shared guard module the redirect and fetch rules will use (no rule in this release reads it yet) treats a same-site path check as complete only when it also refuses a tab or line break after the leading `/`, which browsers drop (`/<tab>/evil.com` goes to `evil.com`), and reads `\xHH` escapes and `{00}` counts correctly in a local-path regex. A bare `x.includes(c)` counts as a refusal only when the slash check also reads the bare `x` (which throws unless `x` is a string): with `String(x).startsWith('/')`, an array `x` (`?next[]=`) would refuse nothing. A regex proving a path segment must not accept `.`, `..` or the empty string, so `^[\w.-]+$` no longer counts.

A project spreading `recommended` sees fewer errors, never new ones.
